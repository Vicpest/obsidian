# 稀疏计算与条件执行

“稀疏”不是一个统一的硬件特性。判断一个 NPU 的稀疏能力时，至少要同时说明：**零/未激活来自哪里、位置是否静态可知、粒度是否规则、以及省下的算力会不会被索引、搬运和负载失衡吞掉**。这些因素决定它能否映射为稳定的端到端收益。

## 四类问题，不应混为一谈

| 类型 | 选择单位 | 位置何时确定 | 主要硬件瓶颈 | 对 Transformer/NPU 的含义 |
| --- | --- | --- | --- | --- |
| 结构化权重稀疏 | 固定小组或 block 中的权重 | 离线（训练/剪枝后） | 压缩格式、选择器、稀疏 GEMM kernel | 最容易形成规则 DMA 与阵列映射；典型为 2:4 |
| 非结构化权重稀疏 | 任意单个权重 | 离线 | 索引读取、间接寻址、PE 负载均衡 | 算术数量下降不等于速度上升；格式和调度成本很关键 |
| 激活稀疏 | token/通道/元素 | 运行时 | 侦测、压缩、动态分派与尾部负载 | 激活函数和模型决定稀疏率；不能假定所有 LLM 激活会产生硬零 |
| 条件计算 / MoE | 整个 expert、token 或层 | 运行时 | 路由、容量控制、All-to-All 与聚合 | 更像编译器/通信系统问题，而非一个 MAC 跳零电路 |

另有“稀疏 attention”：它约束每个 query 可见的 token 集合（例如 block/window 模式），直接改变 `QKᵀ` 的访问图。它与“稀疏权重 GEMM”是两条不同优化路线。

## 结构化 N:M：以 NVIDIA 2:4 为例

N:M 表示沿指定压缩维度的每个连续 `M` 元素组中保留 `N` 个非零值。Ampere Sparse Tensor Core 的公开约束为 **2:4**：每 4 个权重槽位保留 2 个非零值；NVIDIA 官方将其描述为可将该权重侧的存储和带宽接近减半，并在满足支持条件的矩阵乘中提高吞吐。

```text
dense weights:       [w0, w1, w2, w3]
2:4 compressed:      [nonzero_a, nonzero_b] + position metadata
runtime:              metadata 选择对应 activation → 两路 MAC → accumulate
```

这解释了它比任意元素稀疏更易硬件化：每组 work、元数据大小和读写节奏有上界，阵列不会因任意长的索引链而失去规则性。但不要从这一点推出“所有 GEMM 都会 2× 更快”：

- 只有受支持的数据类型、矩阵布局和 kernel 才能走稀疏路径；不合条件时须回退稠密路径。
- 对 LLM，线性层的**权重**可以是 2:4；`QKᵀ` 和 `P×V` 的两侧通常是运行时 activation，不能仅靠权重 2:4 加速。
- 增益还会受 metadata、选择逻辑、矩阵形状、带宽、batch 和量化/稀疏转换成本影响。应报告特定模型、shape、精度与端到端指标，而不是只报告“sparse TOPS”。

模型必须通过结构化剪枝、稀疏感知训练或受约束训练满足模式；精度能否恢复取决于模型、任务和训练配方，不能用一个固定百分比概括。

## 非结构化稀疏：算得少不等于搬得少

COO、CSR/CSC、BCSR 等格式以 value 加位置索引表示非零元。对非结构化 SpMM/SpGEMM，硬件往往需要：读取索引、间接定位下一段数据、重排/聚合操作数、再处理不同 PE 的不等工作量。低稀疏率时，索引与不规则访问的代价可能超过省下的乘法。

因此 NPU 设计应先问：

1. 非零位置能否在编译时静态排程？
2. 压缩后是否真正减少外存字节，而非增加 index 流量？
3. 每个 PE/NoC 链路的工作是否均衡？
4. kernel 能否保持足够大的、规则的 tile？

若这四项没有正面答案，稀疏率本身不是性能证据。

## MoE 与 token 级跳过：系统级的动态稀疏

MoE router 为每个 token 选择少数 expert。它减少的是激活 expert 的计算量，却新增了 Top-K、按 expert regroup、容量限制、跨设备 All-to-All 和负载均衡问题。对多芯片 NPU，关键指标除了 expert GEMM，还包括路由分布、通信字节、尾部 expert 延迟和空专家比例。

Token-level skipping、early exit 与长上下文 sparse attention 同样会引入每 token 不同的执行图。固定数据流阵列可通过分桶、按相同 mask 分组、block 化可见范围和异步队列缓解分歧；若直接让同批 token 任意分支，阵列利用率和调度可预测性都会下降。FlashAttention 的 block-sparse 扩展说明“块规则的 attention 稀疏”可成为实用的 IO 优化；它不等同于支持任意索引 gather 的 DMA。

## 面向 NPU 的实现决策

```text
模型/编译器给出稀疏模式
       │
       ├─ 静态且规则（2:4 / block） ─► 压缩权重 + metadata + sparse GEMM 路径
       │                                   └─ 对齐 DMA、tile 与 fallback
       │
       ├─ 静态但不规则 ─────────────► 评估索引流量、负载均衡和格式阈值
       │
       └─ 动态（MoE / mask / early exit） ─► 路由/分桶/通信调度 + 尾延迟控制
```

- **矩阵引擎**：对规则 N:M 或 block 设计可预测的解压/选择和 MAC 映射；保留稠密 fallback。
- **SRAM/DMA/NoC**：以压缩后字节数、metadata 和实际突发效率建模；随机 gather 不能以顺序带宽估算。
- **运行时**：为 MoE 的 token regroup、expert capacity 和通信完成事件建队列；为动态 mask 保留可表达的 block 描述符。
- **性能模型**：分别测稀疏准备/转换、搬运、计算、通信与尾部同步；roofline 原则见 [[存储层级、调度与性能分析]]。
