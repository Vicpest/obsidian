 稀疏计算：算法免费的午餐，硬件十年的难题

上一篇我们从一个乘法器讲到了 Tensor Core：芯片怎么把每一个数都算出来。这一篇讲一个更诱人的想法——有些数根本不用算。

一个权重矩阵里如果有一半是 0，那一半乘法理论上完全可以跳过，算力直接翻倍，听起来像是白捡的。但"稀疏计算"是 AI 芯片里一个很矛盾的领域：算法上看是免费的午餐，硬件上却是过去十年最难兑现的承诺。学术界围绕稀疏计算提出了大量方案，发过几十篇顶会论文，但工业落地高度分化，真正大规模商用的方案寥寥无几。

稀疏计算中算法收益与硬件代价的核心矛盾

这篇文章想讲清楚的是：稀疏性到底有哪几种，为什么 2:4 这类规则化方案更容易进入通用芯片，以及为什么"跳过零"这件事在硬件里远没有听起来那么简单。
一、稀疏性从哪来：两种源头，三种粒度
1.1 权重稀疏 vs 激活稀疏

深度学习里的"0"主要来自两个地方，硬件难度天差地别。

权重稀疏（Weight Sparsity）：通过剪枝（Pruning）让权重矩阵中大量元素变成 0。这是静态的——模型训练完，哪些位置是 0 就定了。硬件可以在离线阶段就把稀疏权重压缩、建好索引，运行时直接按索引读取。这是对硬件最友好的一类稀疏。

激活稀疏（Activation Sparsity）：经过 ReLU、SiLU 这类激活函数后，一部分激活值变成 0 或接近 0（但非 0）。这是动态的——每个 batch、每个 token 的稀疏位置都不一样，硬件必须在运行时现场判断哪里是 0、现场建索引、现场跳过。这一"现场"是激活稀疏难做的根源。

两个时代的对比很说明问题：

    ‎CNN 时代（约 2014—2020）：ReLU 之后约 60—80% 的激活是 0，激活稀疏率很高。学术界为此提出过大量加速器（Eyeriss v2、Cnvlutin、SCNN 等），但没有一个成为主流商用芯片的标配。
    ‎Transformer 时代（2020 至今）：GeLU、SiLU 不会产生硬 0，只会把值压到接近 0，激活稀疏率显著走低。研究和产品的重心转向了权重稀疏——NVIDIA 在 Ampere 引入的 2:4 稀疏（下一节详说）就是这个方向。

为什么激活稀疏这么难做？三个原因叠在一起：

    判断哪些激活是 0，需要在线计算，天然比离线预处理慢；
    就算知道了 0 在哪，"跳过"本身需要一套按索引跳跃读取的电路，而不是简单地按地址顺序读——这套电路不便宜；
    不同处理单元（PE）分到的稀疏程度不一样，算得快的 PE 要等算得慢的 PE，整体性能被最慢的那个拖住。

这三个问题，在"结构化稀疏"里都能被大幅缓解，这也是工业界普遍转向结构化稀疏的直接原因。
1.2 结构化稀疏的几种粒度

结构化稀疏的思路是：与其允许 0 出现在任意位置，不如限制"0 只能长在哪些地方"，用规则换硬件简单。从最严格到最宽松排开：
粒度
	
规则
	
硬件难度
	
精度损失
Block Sparsity（块稀疏）
	
整个 B×B 的块要么全 0 要么是包含非零元素的密集块
	
最简单——直接跳过整块，访问和调度最规则
	
可能较大（约束最强），取决于块大小、稀疏率、模型与训练方法
Vector Sparsity（向量稀疏）
	
整个 1×V 向量被删除或保留
	
中等，介于块稀疏和细粒度稀疏之间
	
一般中等，依赖具体配置
N:M Sparsity
	
每连续 M 个元素中至多保留 N 个非零值
	
较低，硬件成本可控，但比整块跳过更复杂
	
较小，通常比同稀疏率的大块剪枝更灵活
Unstructured（非结构化）
	
任意元素都可以被置零
	
最难，索引、访存和负载最不规则
	
最小（约束最少），实际精度仍依赖剪枝方法

Block Sparsity 里 B 通常取 16 或 32，OpenAI 早年的 Block-Sparse Attention 用的就是这一路；N:M 里用得最广的是 2:4（每 4 个连续元素里 2 个非零）。

NVIDIA（从 Ampere 起）和 AMD（从 CDNA3 起）都在硬件中支持了 2:4，使它成为 GPU 领域的事实标准；但也有厂商没有跟进——Intel Gaudi 系列就不支持半结构化稀疏加速（截至本文成稿未在官方资料中见支持）。2:4 被选中，原因是它在硬件代价（MAC 阵列面积增加约 5% 量级）和模型精度损失（多数场景 <1%）之间，是目前工程上公认的最优平衡点。

为什么偏偏是 2:4，不是 1:2 或 4:8：1:2 虽然也是 50% 稀疏，但同样稀疏率下，2:4 每 4 元素组有 C(4,2)=6 种非零位置组合，而 1:2 每 4 元素只有 4 种（2×2），2:4 的模式自由度更高、精度损失更小，且元数据开销接近；2:4 每个非零元素只需 2 位索引标注其在 4 个位置中的编号（每组 4 位元数据），与 INT8 这类 8 位数据类型在存储对齐上很自然；4:8 颗粒更细，精度损失更小，但索引位变多（每个非零需 3 位）、硬件选择器更复杂，目前主流商用芯片尚未大规模支持。2:4 是一个工程取舍的产物，不是数学上的最优解——如果未来出现更细粒度（比如 1:4 或 2:8）且成本可控的硬件方案，稀疏度还有继续压缩的空间。
1.3 MoE 的"专家级稀疏"：另一种量级的稀疏

MoE（Mixture of Experts）是稀疏性在一个全新粒度上的体现。每个 token 只激活全部专家中的一小部分，其余专家完全不参与这个 token 的计算——业界称之为专家级稀疏。

以 Mixtral 8×7B 为例：8 个专家中激活 2 个，激活比例 2/8 = 25%（即稀疏度 75%）。DeepSeek-V3 更极端：256 个路由专家中每个 token 只激活 8 个（另有 1 个始终参与计算的共享专家），也就是路由专家里只有 8/256 ≈ 3.1% 被激活。

但 MoE 的稀疏性和前面讲的权重稀疏、激活稀疏是完全不同的两件事：

    ‎粒度极大：不是元素级或向量级，而是整个 FFN 模块（数亿参数）级别；
    ‎跨设备：不同专家通常分布在不同 GPU 上，稀疏体现在 All-to-All 通信里——只有被路由到的 token 才需要跨设备发送；
    ‎动态且难预测：每个 token 该去哪个专家由 Router 实时决定；
    ‎需要统计均衡：训练时要靠 Auxiliary Loss 强制专家被均匀使用，避免某些专家过载、某些专家闲置。

对硬件的要求也随之变成另一套东西：快速的 Top-K 路由电路（详见第四节）、只发送有效 token 的稀疏 All-to-All 通信、每个专家的容量上限与溢出处理、以及同批次内路由到同一专家的 token 能否被合并处理以减少 SRAM 装载次数。

这些需求和传统"稀疏加速器"的芯片设计几乎不搭边。MoE 本质上是"系统层稀疏"而不是"芯片层稀疏"——真正处理它的主要是编译器和通信库（如 DeepSpeed-MoE、Megatron-MoE），而不是某个专用的稀疏计算电路。


二、2:4 结构化稀疏：工业界选中的答案
2.1 NVIDIA Sparse Tensor Core 是怎么做的

NVIDIA 在 Ampere（A100，2020）首次把 2:4 稀疏做进硬件，即 Sparse Tensor Core。核心机制拆开看有三层：

输入约束：权重矩阵必须满足 2:4——每连续 4 个元素恰好 2 个非零。这是硬件强制的：不满足这个约束的权重，无法享受加速，只能退回稠密路径。

元数据格式：4 个权重压缩成 2 个非零值后，还需要记录"这 2 个非零值原本在 4 个位置里的哪 2 个"。做法是给每个非零值配一个 2 位索引（4 个位置用 2 位刚好能编号），2 个非零值就是 4 位索引——这 4 位元数据相对于原始 4 个 INT8 元素（32 位）的开销约为 4/32 = 12.5%。

硬件加速机制：MAC 阵列每个 cycle 只处理 2 个非零权重（而不是 4 个），并根据元数据从对应的激活向量中"挑出"匹配的 2 个激活值参与运算。这一"挑选"由乘法器前的多路选择器（mux）完成，会引入约 1 个 cycle 的延迟，但不影响持续吞吐。

实际加速比：理论上计算量减半，即 2 倍。大矩阵、理想 kernel 条件下可以接近这个数字；但受元数据访问、mux 控制开销、实际 SRAM/HBM 带宽等因素影响，工业界报告的常见实测区间大致在 1.5—1.8 倍的量级，具体取决于矩阵形状和 kernel 实现。

几个容易被忽略的约束：

    2:4 只加速权重侧，激活矩阵仍是稠密的；
    必须搭配 Sparse-aware 训练（下一节详说），否则模型精度会明显下滑；
    不是所有 GEMM 都能吃到这个红利——Attention 里的 QKTQK^T 和 Attn⋅V\text{Attn}\cdot V，两个矩阵都是激活（activation），没有天然可以稀疏化的权重侧，2:4 用不上。

2.2 压缩存储格式：省下的 37.5% 从哪来

2:4 稀疏权重在显存里的实际存储布局：

原始稠密格式（INT8）:
  weight[K][N]: K×N 字节

2:4 稀疏压缩格式:
  values[K][N/2]:   K×N/2 字节     （只存非零值）
  metadata[K][N/4]: K×N/8 字节     （每组 4 位）
  总计: K×N×5/8 字节

存储节省是 1 − 5/8 = 37.5%（不是直觉上的 50%，因为元数据本身要占一部分空间）。这一节省直接换来带宽利用率的提升——同样的 HBM 带宽下能读进来更多有效数据。

编译器要做的事情并不轻松：把训练好的稠密权重转换成 2:4 稀疏格式；把 values 与 metadata 分开存储、按 DMA 友好的方式重新排布内存；在 GEMM 调度时区分每个 tile 是稀疏的还是稠密的；以及处理 fallback——如果某些权重实在满足不了 2:4 约束，退回稠密 GEMM。NVIDIA 提供的 cuSPARSELt 库封装了这些细节，是目前工业界接入 2:4 稀疏最主要的路径。
2.3 训练侧：怎么让模型"长成" 2:4 的形状

一个稠密训练出来的模型不会自动满足 2:4 约束，得靠算法手段"逼"它满足。三条主流路径：

方法一：Magnitude Pruning + Fine-tune。训完稠密模型后，每 4 元素组内只保留绝对值最大的 2 个，其余置 0，再 fine-tune 几个 epoch 找回精度。最简单，但精度损失也最大。

方法二：Sparse-aware Training（STE，Straight-Through Estimator）。训练时前向用 2:4 稀疏权重算，反向梯度照样流过被剪掉的位置。精度损失通常能压到 1% 以内，代价是训练时间有所增加（经验估计约 20% 量级）。

方法三：从头以 2:4 约束训练。从第一天就强制满足 2:4。精度最好，但训练成本最高。

工业界的实际选择：多数生产场景是训完稠密大模型，再用方法二转换为 2:4；也有一些预训练模型直接发布 2:4 稀疏版本（对应方法三），但比例不高。

2:4 稀疏的真实渗透率：据行业公开报道与从业者访谈估计，2:4 稀疏在生产环境 LLM 推理里的使用率大致在 10—20% 的量级，并不算高。主要卡点有三个：一是部分模型（尤其是较小模型）精度损失仍然明显；二是稀疏化训练/fine-tune 这道额外工序增加了部署复杂度；三是同期的量化方案收益更直接——W4A16 这类方案能拿到接近 4 倍的收益，而 2:4 稀疏理论上限只有 2 倍，权衡下来量化经常更划算。

2:4 稀疏真正被寄予厚望的方向是和量化结合——比如 4:8 的 INT4 稀疏组合，相较于 FP16 稠密存储，理论带宽节省可达约 4～6 倍（取决于 metadata 开销的计算方式）。但这个组合目前算法成熟度还早，不算已经落地的能力。
三、非结构化稀疏：一部十年的失败史
3.1 稀疏矩阵存储本身就是硬件难题

学术界对非结构化稀疏（任意位置都可以是 0）的加速研究持续了十年以上，但工业商用始终没打开局面。问题的根子在存储格式。

常见的四种稀疏矩阵格式：

    ‎COO（坐标格式）：每个非零元素记 (row, col, value) 三元组，最简单，但元数据开销很大；
    ‎CSR（压缩稀疏行）：‎values[] 存所有非零值，‎col_idx[] 记每个非零值的列号，‎row_ptr[] 记每行第一个非零元素在 values 里的位置——适合按行访问，是 GPU 稀疏 GEMM 的默认格式；
    ‎CSC（压缩稀疏列）：CSR 的列版本；
    ‎Block CSR（BCSR）：把矩阵切成 B×B 块，块内全 0 就不存、否则整块稠密存储，在中等稀疏度（50—90%）区间比 CSR 更高效。

真正的难点在稀疏 GEMM 的核心操作：对 A 中的每个非零元素，要在 B 里找到对应行的非零元素相乘。这个"对应查找"在硬件里要做四步——读 A 的列索引、用列索引去定位 B 的对应行、在 B 的这一行里再找非零位置（这是第二次稀疏访问）、最后才能算并累加。每一步都是非顺序的内存访问，直接打乱了硬件原本靠预取和缓存吃到的红利。这是非结构化稀疏效率始终上不去的根本原因——不是算得慢，是"找"得慢。

3.2 学术加速器为什么没能走向商用

非结构化稀疏的另一个核心问题是负载不均：如果按行把矩阵分给不同 PE，稀疏密度高的行很快算完，密度低的行拖后腿，整体吞吐取决于最慢的那个 PE。

学术界针对这个问题提出过不少方案：SCNN（ISCA 2017，元素级稀疏 + 笛卡尔积乘法，PE 间动态分发非零元素）、Cambricon-S（MICRO 2018，硬件级稀疏-稀疏 GEMM 加速）、SIGMA（HPCA 2020，基于可重构互连的稀疏 GEMM 加速器）、SparTen（MICRO 2019，内积级稀疏匹配）。

这些工作有一个共同特点：在仿真器上表现不错，但没有一个走到大规模商用芯片里。原因不是单一的：

    路由 / 调度这类"找非零"的逻辑本身有硬件开销，往往吃掉了稀疏带来的大半收益；
    配套的编译器栈异常复杂，工业化部署难度极高；
    算法侧 2:4 结构化稀疏 + 量化的组合已经能满足大部分需求，做非结构化稀疏的动力不强；
    客户对"加速比"宣传的可复现性要求很高，而非结构化稀疏在不同模型上的实际加速比差异很大，不好对外承诺一个稳定数字。

3.3 工业教训：Cerebras、Graphcore 走过的路

近十年宣称支持"非结构化稀疏加速"的商业 AI 芯片，大多没能把这条路走通。

Cerebras WSE：晶圆级芯片，早期宣传里包含对非结构化稀疏的支持。但实际部署中，客户真正看重的是单芯片的超大容量和高速 SRAM，从公开信息看，稀疏加速本身的收益并不突出。Cerebras 后来的产品重心也转向了"全 SRAM 大模型推理"（Cerebras Inference），而不是继续强调稀疏加速能力。

Graphcore IPU：曾大力宣传对非结构化稀疏的原生支持。2024 年 7 月，Graphcore 被软银集团收购，成为其全资子公司，公开报道的收购价格约 5—6 亿美元，远低于其此前约 27.7 亿美元的估值峰值。

这里没有把这两家公司的结局简单归因于稀疏路线的失败——芯片公司的兴衰是多个因素叠加的结果。但它们的经历共同指向一个更普遍的教训：硬件功能的价值取决于算法生态是否真的采用它。如果主流算法并不依赖某个硬件特性（比如非结构化稀疏），这个特性即便技术上做出来了，也很难在商业上收回投入的硅面积成本。这对芯片设计团队的启示是：需要持续跟踪算法演进的方向，避免为"技术上漂亮但生态不买账"的功能投入过多资源。
四、动态稀疏与条件计算：LLM 时代的新问题
4.1 Top-K 选择：MoE Router 的硬件核心

MoE 的 Router 以及许多动态稀疏算法，都要用到 Top-K 选择——从 N 个候选里挑出最大的 K 个。这是一个看似简单、实则很值得细看的硬件问题。

几种典型实现思路：

    ‎朴素的部分排序：复杂度 O(NK)，N 较小（8—64）时可行；
    ‎Bitonic Sort（双调排序）：先完全排序再取前 K，复杂度 O(N log²N)，但可以完全并行化，硬件网络结构非常规整，适合做成 ASIC；
    ‎堆排序 / 部分排序：维护一个大小为 K 的堆，新元素只跟堆顶比较，复杂度 O(N log K)；
    ‎基于归约的 Top-K：把 N 个元素分组，每组先选出局部 Top-K，再逐层归约，适合 GPU 上 Warp 级别的并行实现。

三种实践场景对应不同选择：MoE 的 Top-K（N 通常是 8、32、256，K 是 1、2、8）一般用部分排序或硬件比较树，追求 1 个 cycle 内完成；Beam Search 的 Top-K（N 大、K 小）更适合用堆；推荐系统场景（N 可能到 10610^6 量级，K=10）则通常改用近似最近邻搜索算法（效果上等价于近似 Top-K，如 HNSW、ScaNN），不再追求精确解。Hopper/Blackwell 上 MoE Router 的具体硬件实现 NVIDIA 并未公开细节，但从指令吞吐推测应是一套规整的硬件比较树——这是 MoE 推理里一个不起眼但处在关键路径上的硬件单元。
4.2 早退（Early Exit）：为什么 GPU/NPU 天生不擅长

早退算法在网络中间层判断"是否已经能给出答案"，能的话就提前退出，不再往下算。代表算法包括 CNN 上的 BranchyNet、Transformer 上的 DeeBERT、CoLT5。

早退给硬件出的难题是动态控制流：每个样本的退出判断是独立的；退出条件（softmax 概率、熵、或自定义 head）需要在线计算；一旦退出，后面的层完全不执行，硬件必须能中途 abort 流水线。

GPU/NPU 结构性地不擅长这件事，原因有三层：GPU 的 SIMT 模型假设同一批（batch）内所有样本走相同路径，早退会导致 warp divergence——一半样本继续、一半退出，硬件只能把两条路径串行跑完；NPU 的固定数据流假设每一层都会被执行，中途跳出意味着硬件状态要处理"半途而废"的情况；编译器也没法静态优化，因为计算图本身变成了动态的。

结果是理论收益在实际部署里会打折扣：一个理论上能省 30% 算力的早退方案，落到 GPU 上可能只省 10—15%（示意量级）。如果端侧 LLM（延迟敏感、batch 通常等于 1）大规模采用早退，可能会催生专门支持动态控制流的硬件，但这条路目前还在早期探索阶段。
4.3 Token-level Skipping 与稀疏 KV-Cache

长上下文 LLM 推理带来了另一类动态稀疏：Token 级跳过。基于注意力分数的稀疏化方案（比如 Longformer 的滑动窗口、StreamingLLM 的 attention sink）让每个 token 只关注历史中的一小部分，而不是全部。

好处很直接：Attention 的计算量从 O(N2)O(N^2) 降到 O(N⋅W)O(N \cdot W)（WW 是窗口大小），在 128k+ 的长上下文场景下收益非常可观。

但硬件上的挑战也不小：注意力 mask 是动态的，不同 token 有不同的 mask 模式，硬件需要支持灵活的 mask 生成；KV-Cache 的访问模式从顺序读变成了跳跃读；同一 batch 内不同 token 的"有效历史长度"可能长短不一。

这里有一处需要纠偏的细节：Hopper 引入的 TMA（Tensor Memory Accelerator）常被简单地描述为"支持任意访问模式"，但严格说并不准确。TMA 的实际能力是高效搬运多维、带步长（strided）的张量分块——支持 1D 到 5D 的结构化拷贝，并能在同一 Cluster 内的多个 SM 之间做多播（multicast），核心目的是把地址计算、步长处理这些琐碎工作从线程里卸载到专用硬件单元。这是"结构化的批量搬运"，不是逐元素的任意索引 gather。滑动窗口、StreamingLLM 这类算法能在 Hopper 上高效实现，靠的是在 TMA 的分块拷贝原语之上，由 kernel 自己组织好访问的分块与步长，而不是 TMA 天然具备任意索引能力。这个区别不影响"Hopper 之后这类算法效率明显提升"的结论，但值得说清楚，避免把工具的能力边界想象得过大。

一个值得关注的方向：随着上下文长度继续往百万 token 级别走，未来的 AI 芯片可能需要更原生地支持"稀疏 KV-Cache 访问"——硬件级的索引解析、跳跃式 DMA、动态 mask 生成会变成标配而不是特例。这一层在 Blackwell 上仍未完全成型，是下一代芯片值得观察的创新点。
小结：稀疏 TOPS 数字，怎么看才靠谱

稀疏计算是 AI 芯片设计里理论收益最大、工程实现最难、商业回报最不确定的一个领域。这一篇建立的核心认知，收拢成几句话：

    稀疏性可以从来源（权重 / 激活 / MoE）、粒度（块 / 向量 / N:M / 非结构化）、时态（静态 / 动态）三个维度去分类，不同维度组合对硬件的要求天差地别；
    ‎结构化稀疏，尤其是 2:4，是工业界的一个妥协方案——硬件代价可控、精度损失可接受、生态相对成熟，但实际渗透率并不算高；
    ‎非结构化稀疏的商业化历史基本是一系列失败教训——根源是硬件能力和算法生态之间长期错配；
    ‎MoE 是一种全新形态的稀疏——粒度极大、跨设备、动态路由，主要靠通信库和编译器处理，不是芯片电路层面的稀疏；
    ‎动态稀疏（早退、Token-level Skipping）是 LLM 时代冒出来的新方向——但和传统的静态数据流硬件天然不兼容，需要架构层面的新突破。

如果只带走一个判断标准，建议是这个：拿到一款 AI 芯片宣传的"稀疏 TOPS"数字时，先问一句——它对应的是哪种稀疏（权重级的 2:4，还是宣称支持的非结构化稀疏），是静态的还是动态的，以及这个数字背后有没有算法生态的真实支撑。分得清这几件事，就能大致判断这个数字有多少是"几乎免费"，多少是"看起来诱人、实际很难兑现"。
